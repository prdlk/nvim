# Create user stories

Write user stories with acceptance criteria for the feature or change described below.

## Steps

1. If the feature touches an existing codebase, read the relevant code so the criteria reflect current behavior, names and constraints.
2. Split the work into stories that each deliver one testable outcome. Name the user or role actually affected, which may be a developer or operator.
3. Write in plain, concise language that product, development, operations and QA all read the same way. Note open questions instead of guessing.

## Output

For each story:

```
### <Short title>

As a <role>
I want <capability>
So that <benefit>

Acceptance criteria
- Given <context>, when <action>, then <observable result>.
```

- Cover the normal path plus the error and edge cases that matter; keep each criterion testable and unambiguous.
- Add a final "Notes" line only when another team must be told (for example operations for a migration).
